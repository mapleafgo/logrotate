# Go logging buffers: ownership, overload, and shutdown

**Bottom line:** lumberjack rotates files synchronously, zap batches bytes, and zerolog diode decouples the producer by allowing unread entries to be lost. The local async writer decouples the producer too, but never overwrites a write it has accepted. The upstream tags below are research pins, not dependencies of this module.

| Implementation | Buffer ownership and capacity | What happens under load |

The caller's bytes go directly to the active file while holding the logger mutex. | Writers can wait for the mutex, rotation, or file I/O. A single write larger than the maximum file size returns an error; crossing the limit rotates before writing. |

## Delivery, errors, and shutdown

- **Lumberjack:** its background mill is for backup compression and cleanup, not log submission. A single-slot, nonblocking notification coalesces maintenance requests. Close closes the current file; the implementation neither drains a payload queue nor exposes a Sync method. [File close](https://github.com/natefinch/lumberjack/blob/v2.2.1/lumberjack.go#L154-L169) · [Maintenance worker](https://github.com/natefinch/lumberjack/blob/v2.2.1/lumberjack.go#L351-L372)
- **Zap:** the ticker (default 30 seconds) calls Sync, which flushes the buffer and calls the wrapped Sync. Tick errors are ignored by the loop; bufio retains write/flush errors, but a transient wrapped Sync error is not separately saved. Stop ends the periodic loop and does a final Sync on the normal initialized shutdown path; it does not close the wrapped sink. Stop does not make Write reject new writes, so stop producers first. [Sync and Stop](https://github.com/uber-go/zap/blob/v1.27.0/zapcore/buffered_write_syncer.go#L149-L209)
- **Diode:** the worker ignores the sink's write count and error. After a consumed entry's sink Write returns, buffers with capacity at most 64 KiB can go back to the pool. Overwritten/skipped entries do not go through that pool-return path. That cap is for pool recycling, not a per-entry limit. Close cancels and joins the consumer, then closes the sink if it implements io.Closer. The [poller](https://github.com/rs/zerolog/blob/v1.34.0/diode/internal/diodes/poller.go#L53-L67) and [waiter](https://github.com/rs/zerolog/blob/v1.34.0/diode/internal/diodes/waiter.go#L56-L75) both try to read before checking cancellation on a miss; there is no producer admission gate, delivery barrier, or guarantee that every successful Write is delivered. [Writer lifecycle](https://github.com/rs/zerolog/blob/v1.34.0/diode/diode.go#L71-L109)
- **Local:** Write success means accepted into the queue, not delivered or persisted. One worker calls the sink once per data entry, converts a nil-error short write to io.ErrShortWrite, and preserves the first delivery error even though LastError can clear on a subsequent success. Sync inserts a FIFO barrier that waits for admission even under FullDropNewest and returns the first earlier delivery error and/or the current sink Sync error. Close closes admission, wakes waiting writers, and waits for accepted messages to be processed before closing the sink. It reports the first delivery error and/or the sink close error; it has no timeout and does not implicitly Sync. [Worker](../async.go) · [Error reporting and shutdown](../async.go)

## Implications for the local writer

- Copy on admission is the ownership boundary. A pool could reduce allocation churn, but only release a buffer once the synchronous sink Write returns, and cap the capacity retained by the pool. Neither a pool nor counting queue entries gives a total queued-byte budget.
- Treat batching and overload as separate choices. The local worker sends one sink Write per accepted record. Combining records into a single write can change rotation boundaries or trigger a maximum-write-size error on a size-based sink such as lumberjack. Adding a diode-style overwrite policy would also change which records a successful Write protects.
- Keep the meanings of **accepted**, **delivered**, and **synced** distinct. For explicit synchronization before shutdown, stop producers, call and check Sync, then call and check Close; actual persistence depends on the sink's Sync implementation.
