# Logback 可靠性调研

范围：Logback 官方在线 manual 与固定版本 **1.5.18** 源码；压缩失败细节核对 GZIP/ZIP，不外推到 XZ、其他版本或自定义策略。以下为源码走读，未做 JVM 故障注入。

## AsyncAppender：丢弃、阻塞、停机

- **默认并非无损背压。** 队列默认 256 条，未设置阈值时取整数除法 `queueSize / 5`。入队前若剩余容量**严格小于**阈值，classic 丢弃 TRACE、DEBUG、INFO，WARN/ERROR 不走此分支。`discardingThreshold=0` 只关闭提前丢弃。见 [官方 manual](https://logback.qos.ch/manual/appenders-async-sift.html)、[队列初始化](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/AsyncAppenderBase.java#L50-L66)、[阈值与入队](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/AsyncAppenderBase.java#L147-L180)、[classic 的级别判断](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-classic/src/main/java/ch/qos/logback/classic/AsyncAppender.java#L30-L47)。
- **满队列行为独立于阈值。** `neverBlock=false`（默认）使用循环 `put`；生产者被中断后继续等待，成功入队后恢复中断标志。`neverBlock=true` 使用 `offer`，忽略返回值；满时连 WARN/ERROR 也能丢，调用方拿不到逐条结果。关闭提前丢弃且保留阻塞，仅意味着正常运行时不因队列策略丢弃，不是交付保证。见 [源码](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/AsyncAppenderBase.java#L147-L180)。
- **停机超时限制等待，不强杀 worker。** manual 建议停止 LoggerContext；`stop()` 标记停止、interrupt daemon worker，再 `join(maxFlushTime)`（默认 1,000 ms；0 为无限等待）。worker 退出消费循环后尝试交付剩余事件并解除下游 appender；超时只记录“可能丢弃”的告警，不清空队列、不再次取消 worker，因此 worker 可能在 stop 返回后继续；JVM 退出仍可能遗失队列或已取出的批次。该路径没有生产者准入封口并等待在途 put 的协议，停机前宜先停止产生日志。见 [manual](https://logback.qos.ch/manual/appenders-async-sift.html)、[启动和停止](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/AsyncAppenderBase.java#L101-L145)、[worker](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/AsyncAppenderBase.java#L264-L294)。

**对照本库。** [异步写入](../async.go)使用有界 FIFO，默认满队列阻塞；显式选择 `FullDropNewest` 才拒绝当前记录并返回 `ErrDropped`。关闭停止接纳、唤醒等待者，排空已入队的记录后关闭底层，不隐式调用 `Sync`，也没有内置等待上限。

## TimeBasedRollingPolicy：压缩失败、续跑、重试

- **切换活动文件与压缩完成分开。** 周期边界后首条事件触发滚动，而非定时任务；压缩模式由 pattern 后缀决定。配置固定 `file` 时先尝试重命名活动文件为带纳秒后缀的 `.tmp`（它是压缩**输入**），再提交压缩；不配置 `file` 时以到期周期的文件作为输入。Appender 关闭旧流、执行滚动、尝试打开活动文件，不等待压缩成功。同步 `RolloverFailure` 被捕获并以追加模式尝试重新打开，告警里的 “Deferring roll-over” 不是旧压缩任务重试。见 [manual](https://logback.qos.ch/manual/appenders-rolling.html)、[滚动策略](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/rolling/TimeBasedRollingPolicy.java#L147-L177)、[Appender](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/rolling/RollingFileAppender.java#L176-L232)。
- **GZIP/ZIP 压缩失败不保证原件仍在。** 缺输入或目标已存在时预检告警并返回；进入压缩后直接写最终归档名，流的打开、读写或关闭异常会写 ErrorStatus，但两个策略均在 catch 后继续尝试删除输入。因此 I/O 失败可能留下部分归档，也可能删掉原始文件；不能把最终文件存在或 Future 正常完成当作压缩成功。见 [GZIP](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/rolling/helper/GZCompressionStrategy.java#L32-L66)、[ZIP](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/rolling/helper/ZipCompressionStrategy.java#L35-L80)、[任务提交](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/rolling/helper/Compressor.java#L104-L125)。
- **继续记日志不等于恢复旧归档。** 默认触发器先推进周期状态；启动时可用可读的固定活动文件 mtime 初始化周期，但 policy 启动没有扫描并重放遗留压缩任务。`cleanHistoryOnStart`（默认 false）只调度历史归档清理，后续滚动只提交当次压缩，未见失败回调、定时退避或重启回放。每次提交覆盖对应 Future 字段，`stop()` 对保存的压缩和清理 Future 分别限时等待，异常/超时只报状态，不重提任务。见 [默认触发器](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/rolling/DefaultTimeBasedFileNamingAndTriggeringPolicy.java#L44-L56)、[mtime 初始化](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/rolling/TimeBasedFileNamingAndTriggeringPolicyBase.java#L74-L95)、[启动/停止](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/rolling/TimeBasedRollingPolicy.java#L61-L133)、[提交](https://github.com/qos-ch/logback/blob/v_1.5.18/logback-core/src/main/java/ch/qos/logback/core/rolling/TimeBasedRollingPolicy.java#L147-L177)及 [manual 的 cleanHistoryOnStart](https://logback.qos.ch/manual/appenders-rolling.html)。

**对照本库。** [Writer](../rolling.go) 启动时唤醒归档维护，每次封存也发出可合并的通知。维护 goroutine 每轮扫描归档目录并排除正在封存的输入，失败结果由 `Writer.MaintenanceError()` 报告，并在没有新通知时按 1、2、4 秒最多重试三次；新通知会重置预算。Close 等待维护 goroutine 退出，不等待尚未触发的重试。当前规则见[使用说明](../README.md)。

与 Logback 不同，本库不用内存任务表示未完成的归档：待处理原件以 `.pending` 留在磁盘上，重启后按盘上状态重做。新 gzip 先写同目录 `.tmp`，发布为 `.gz` 后才删除原件；发布前若已存在同名 gzip，则校验其内容与原件一致后才会移除原件。空间不足（`ENOSPC`）时，若保留清理腾出了空间，同一轮会补试一次。

**结论：** 可用 Logback 对照队列背压与滚动/压缩分离，但不宜把它的提前丢弃、停机等待上限或 GZIP/ZIP 失败处理当成当前 Go 实现的等价契约。Go 的续跑依赖落盘 pending，定时重试有预算；两者都不是进程异常退出时的无损承诺。
